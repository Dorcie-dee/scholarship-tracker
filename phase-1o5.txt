==================================================
1. QUALITY CODE IS A REQUIREMENT
==================================================

Do NOT optimize merely for "the endpoint returns the correct response."

An endpoint can technically work while still being poor-quality engineering.

For example, avoid inefficient service logic such as:

request
 ↓
DB query
 ↓
another DB query
 ↓
another DB query
 ↓
another DB query
 ↓
combine results in JavaScript

when the same result can reasonably be obtained through:

- one well-designed query
- appropriate joins
- TypeORM relations
- QueryBuilder
- batching
- carefully designed projections/selects
- appropriate indexes
- or another clearly justified approach.

However, do NOT blindly force everything into one enormous query either.

The objective is:

OPTIMAL DATABASE ACCESS

not:

"Always exactly one query."

Use engineering judgement.

==================================================
2. DATABASE ROUND-TRIP DISCIPLINE
==================================================

For every nontrivial service method or endpoint, inspect how many database queries it causes.

I want you to actively identify:

- N+1 query patterns
- repeated queries for the same entity
- redundant existence checks
- unnecessary sequential queries
- loading entire entities when only a few fields are needed
- fetching related data separately when a join/relation could reasonably handle it
- unnecessary save() calls
- unnecessary reloads after save()
- redundant count queries
- redundant transactions
- queries that could be combined
- queries that could be parallelized where appropriate
- unnecessary application-side filtering when PostgreSQL can efficiently filter it

Do not assume that because TypeORM abstracts SQL, the database cost is irrelevant.

TypeORM code must still be evaluated based on the SQL/database behaviour it produces.

==================================================
3. PERFORMANCE MUST BE CONSIDERED IN EVERY SERVICE
==================================================

For every meaningful service function, ask:

1. How many DB round trips does this require?
2. Is every query necessary?
3. Can any queries be combined?
4. Can independent queries safely execute in parallel?
5. Is the query retrieving more data than necessary?
6. Are appropriate indexes available?
7. Could this become an N+1 problem as data grows?
8. Is there unnecessary object transformation?
9. Is there unnecessary network traffic?
10. Is the operation inside an appropriate transaction where required?
11. Is the transaction unnecessarily large?
12. Is the operation idempotent where appropriate?
13. What happens when the dataset grows from 10 records to 10,000 or 1,000,000 records?

Milliseconds matter.

Database calls, network round trips, serialization, memory use and unnecessary computation all contribute to the quality and reliability of the platform.

Do not prematurely optimize microscopic operations where there is no meaningful benefit.

But do not ignore obviously inefficient database access.

Use evidence and reasoning.


==================================================
4. SERVICES WITH MULTIPLE FUNCTIONS
==================================================

If a service contains more than two meaningful functions, review the functions individually.

Do not automatically create multiple DB calls just because the code has been split into helper functions.

For example, avoid:

createApplication()
    ↓
checkUser()
    ↓ DB query

checkOpportunity()
    ↓ DB query

checkJourney()
    ↓ DB query

saveApplication()
    ↓ DB query

when the necessary information could reasonably be obtained more efficiently.

At the same time, do not combine unrelated responsibilities into one massive function merely to reduce query count.

Maintainability and performance must both be considered.

If there is a trade-off, explain it to me before making the change.

[x] C3 / I6 — Opportunity -> Application Requirement one-time copy, with
    copiedFromRequirementId provenance (self-FK, ON DELETE SET NULL,
    deliberately not indexed). Atomic with Application creation in one

[x] CRITICAL FIX — Cloudinary deletion ordering. DocumentsService.remove()
    used to delete the Cloudinary asset BEFORE the Postgres row, which
    ON DELETE RESTRICT on application_documents.document_id made
    deterministically unsafe for any attached document: the real file was
    destroyed, the DB delete then failed, and the caller only ever saw a
    generic 500. Reordered: ownership check -> three concurrent eligibility
    checks (attached / snapshot-referenced / has a dependent child), each a
    clean 409 -> DB delete (+ current-version promotion, same transaction)
    -> only then, Cloudinary delete. A Cloudinary failure after a successful
    DB delete is logged for operational follow-up and never reverses the
    already-committed DB deletion.
[x] D1 — concurrent uploadNewVersion() race fixed: the version-determining
    read now happens inside the transaction against a row locked with
    SELECT ... FOR UPDATE, with isCurrent re-checked post-lock. The loser of
    a race gets a clean 409, never a silently-created duplicate-numbered
    sibling.
[x] D-P2 — version-chain integrity: Document.previousVersionId's FK changed
    from ON DELETE SET NULL to ON DELETE RESTRICT — a version a newer
    version depends on can no longer be deleted, at either the DB or
    service layer.

[x] D-P3 — current-version deletion promotes the previous version in the

[x] D-P4 — ApplicationDocument detach implemented:
